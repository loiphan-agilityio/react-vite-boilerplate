# boilerplate (monorepo)

A pnpm + Turborepo monorepo. `apps/` holds the web apps, `packages/` the shared packages they
use. The app's stack and rules are in `apps/web/CLAUDE.md`.

## Layout

```
apps/
  web/                  the app (package `web`): React SPA, its API layer, tests, mocks, Storybook
packages/
  ui/                   @repo/ui (source-only): the UI kit every app shares
    src/components/       shadcn components, generated by the shadcn CLI: never edit by hand
    src/lib/utils.ts      cn()
    src/styles/globals.css  Tailwind 4 theme tokens, fonts, base layer
  typescript-config/    @repo/typescript-config: base.json, react.json, node.json
tools/oxlint/anti-slop/ anti-slop's Oxlint rules, vendored (UPSTREAM.md: source, commit, changes)
oxlint.config.ts        the one linter's rules (Oxlint): ESLint's, typescript-eslint's (type-aware
                        through oxlint-tsgolint), React, jsx-a11y, Storybook, anti-slop; no ESLint
package.json            root scripts (turbo) and commitlint config; lint-staged.config.mjs
tsconfig.json           types for the root's own TypeScript (oxlint.config.ts), which the
                        type-aware lint rules need
pnpm-workspace.yaml     workspace packages (apps/*, packages/*), pnpm settings, the catalog
turbo.json              task graph, caching, env (VITE_*) and inputs (.env*)
.github/workflows/ci.yml  CI/CD: gates, Cloudflare Pages deploy of apps/web, Lighthouse, production, then e2e on it
.husky/                 pre-commit (lint-staged, then pnpm typecheck), commit-msg (commitlint),
                        pre-push (refuses main, dev, stag, prod and their long names)
.claude/                settings.json: the pnpm commands Claude runs without a permission prompt,
                        and a hook that runs Prettier on each file Claude writes (hooks/format.mjs).
                        Claude Code reads it only in sessions started here; apps/web/.claude/
                        settings.json does the same for sessions started in the app
.prettierrc.json, .prettierignore, .gitignore, .gitattributes, skills-lock.json
```

## Commands

From the root, each runs through turbo in every package that has the script:

| Command | What it does |
|---|---|
| `pnpm dev` | `web` dev server. `pnpm dev:mock` serves its API from MSW mocks. |
| `pnpm lint` | Oxlint (`oxlint.config.ts`, `--type-aware --deny-warnings`) and `prettier --check` in each package, then `lint:root`, the same two on what no package checks: everything outside `apps/` and `packages/` (`tools/`, `create/`, `.github/`, the configs). `pnpm lint:fix` fixes and formats (uncached). |
| `pnpm typecheck` | Type-check. |
| `pnpm test` | Vitest, with coverage. |
| `pnpm test:watch` | Vitest in watch mode: re-runs the tests a saved file affects, until stopped. Keep it running in a terminal of its own while writing code. |
| `pnpm build` | Production build (apps only; packages have no build). |
| `pnpm build-storybook` | Static Storybook build. |
| `pnpm test:e2e` | Playwright end-to-end tests on the mocked build (uncached). `pnpm test:e2e:install` downloads Chromium once per machine. |
| `pnpm check` | All six gates, in two turbo runs: `lint lint:root typecheck test`, then `build build-storybook test:e2e`. Run at once, they starved vitest's workers on an 8 GB laptop ("Failed to start forks worker"), and a failing cheap gate now stops before the builds. `TURBO_FORCE=true pnpm check` reruns cached gates (`--force` would reach the second run only). **Run before calling work done.** |
| `pnpm lighthouse <url>` | Lighthouse 13.5 (mobile) on a deployed or previewed page (`pnpm build`, then `pnpm --filter web preview`): accessibility under 100 or SEO under 95 fails, performance and best practices warn (`tools/lighthouse.mjs`). Reports in `lighthouse/`. CI runs it on each preview deploy. |
| `pnpm test:tools` | The tests of `tools/lib/` (what `check:report` and `lighthouse` conclude from their tools' output), and a guard that the anti-slop rules still report after an Oxlint update. Node's test runner; CI's check job runs them. |
| `pnpm check:report` | The gates of `pnpm check` one after another, going on after a failure, then the output checklist: each gate pass/fail, the unit and e2e pass rates (%), line coverage and times (`tools/check-report.mjs`; `--only` / `--skip` pick gates). Markdown on stdout and in CI's run summary, JSON in `check-report.json`. |

- One package: `pnpm --filter <name> <script>` (`pnpm --filter web storybook`), or run the
  script from inside the package (`cd apps/web`, then `pnpm storybook`).
- Run each command on its own, exactly as written (no pipes or redirects): the tool result
  already holds the output and the exit code.
- Tasks run in parallel. A `transit` task (no script) makes a change in a source-only package
  invalidate the cache of every package that depends on it.

## Dependency direction

- Apps depend on packages, never packages on apps. No cycles between packages.
- Packages are source-only (no build step) and are consumed through their `package.json`
  `exports` only (`@repo/ui/components/button`, `@repo/ui/lib/utils`, `@repo/ui/globals.css`),
  never through a relative path into another package.
- App-specific code stays in the app: its features, its API layer (`src/lib/api`), config,
  mocks and test helpers. Move code into a package only when a second app needs it (see the
  roadmap below).

## Catalog rule

Every dependency declared by two or more workspace packages uses the range `catalog:`; its
version lives once in `pnpm-workspace.yaml`. React and sonner must resolve to a single copy:
sonner's toast store is module-level, so two copies mean toasts that never show.

## Skills

The web-dev skills (`develop`, `feature-development`, `api-integration`, `ui-development`) refuse
the monorepo root: run them from inside the app (`cd apps/web`). They treat an app as tier
`template` only if its `package.json` declares `react`, `vite`, `effect`, `@tanstack/react-query`
and `react-hook-form`, `src/lib/api/client.ts` contains `ApiClient`, and `src/test/render.tsx`
exists. The app's `package.json` also keeps `packageManager`: it is how the skills know it is pnpm,
since the lockfile is at the root. `apps/web` must keep all of these.

- Never scaffold with `project-setup` (or `develop`'s new-app route) inside this repo: its template
  is a standalone app with its own lockfile, workspace file and hooks. Use "Recipe: add an app".

## Recipe: add an app

1. Create `apps/<name>/package.json`: private, `"type": "module"`, `packageManager`, the same
   scripts as `apps/web`, shared dependencies as `catalog:`, workspace packages
   (`@repo/ui`, `@repo/typescript-config`) as `workspace:*`. Copy what
   those scripts need from `apps/web`: `index.html`, `public/` (the `msw init` target),
   `.storybook/`, `src/main.tsx`, `src/test/`, `src/mocks/`, `.env.example`, `.env.mock`.
2. Lint comes from the root `oxlint.config.ts` (its `lint` script: `oxlint -c ../../oxlint.config.ts
   --type-aware`); its globs start with `**/`, so they hold for any app. Add an override that
   points `storybook/no-uninstalled-addons` at the new app's `package.json`, as `apps/web` has
   (lint-staged runs Oxlint from the root).
3. `tsconfig.app.json` and `tsconfig.node.json` extending `@repo/typescript-config`; `types`
   and `paths` stay in the app. The solution `tsconfig.json` maps `@repo/ui/*` plus the exact
   `@repo/ui/globals.css` entry (copy them from `apps/web/tsconfig.json`).
4. `components.json` in shadcn monorepo mode, with `tailwind.css:
   '../../packages/ui/src/styles/globals.css'` and the aliases `utils: '@repo/ui/lib/utils'` and
   `ui: '@repo/ui/components'`, so `pnpm exec shadcn add` writes into `packages/ui`.
5. `src/styles/index.css`: `@import '@repo/ui/globals.css';` then `@source '..';`.
6. Its own `.prettierignore`, and a Vite config (start from `apps/web/vite.config.ts`).
7. For the web-dev skills, the template markers listed under Skills.
8. `pnpm install`, then `pnpm check`.

## Recipe: add a package

1. `packages/<name>/package.json`: name `@repo/<name>`, private, `"type": "module"`, a
   source-only `exports` map (no build), scripts `lint`, `lint:fix`, `typecheck` (and `test`
   when it has tests), shared dependencies as `catalog:`.
2. A `tsconfig.json` extending `@repo/typescript-config` (the type-aware rules read it), a `lint`
   script running `oxlint -c ../../oxlint.config.ts --type-aware --deny-warnings .` and
   `prettier --check .`, and its own `.prettierignore`.
3. Each consumer adds `"@repo/<name>": "workspace:*"`.
4. `pnpm install`, then `pnpm check`.

## Commits

- Conventional Commits: `type(scope): summary`. The `commit-msg` hook (commitlint) rejects
  anything else.
- The hooks live in the root `.husky/` and run from the root: `pre-commit` runs lint-staged
  (Oxlint and Prettier on the staged files), then `pnpm typecheck` (turbo, every package);
  `pre-push` refuses a push to `main`, `master`, `dev`, `develop`, `stag`, `staging`, `prod`
  and `production` (`PROTECTED_BRANCHES="a b"` replaces the list): those change through a
  reviewed pull request.
  Fix what they report; never commit with `--no-verify`.

## CI/CD and deploy

`.github/workflows/ci.yml` runs on pull requests and pushes to `main`, from the root:

1. **check** (lint, typecheck, unit tests with coverage, build, Storybook build, and the mock
   build the deploys publish).
2. **deploy-draft**: the mock build and the Storybook **check** built go to
   Cloudflare Pages as a preview (`pr-<number>.<project>.pages.dev` on a pull request, branch
   `main-draft` on a push to `main`), without building them again, with
   `wrangler pages deploy apps/web/dist`. `apps/web/public/_headers` (copied into both builds)
   holds the headers; Pages serves `index.html` for any path that is not a file, and
   `apps/web/public/assets/404.html` makes a missing chunk a 404 instead (never add a top-level
   `404.html`: it turns that fallback off). Each preview also sends `X-Robots-Tag: noindex` (the job
   adds it to the `/*` block of its copy of `_headers`: Pages keeps one rule per path, so a
   second `/*` block would drop the security headers), so a leaked preview URL stays out of
   search results; production is deployed without it.
3. **lighthouse**: `tools/lighthouse.mjs` on the preview (mobile; accessibility 100 and SEO 95
   or more required, performance and best practices reported), its scores in the run summary.
4. **deploy-production** (push to `main`): the same files go live (a deploy to the project's
   production branch, `main`), only after Lighthouse passed.
5. **e2e** (push to `main`): the only E2E run. After production is live, `pnpm test:e2e` runs
   against its URL (`E2E_BASE_URL`). It gates nothing, since it runs after the release.

GitHub lists each check as `CI / <name> (<event>)`, from the job's `name:`:
`Checks: lint, typecheck, unit, build`, `Deploy: preview`, `Lighthouse: deployed preview`,
`Deploy: production`, `E2E: production`. `needs:` and `if:` use the job ids above.
A required status check in branch protection matches that name, so after renaming a job, select
it again there. The two deploy jobs add a commit status, `Preview - Webapp Deployment` and
`Prod - Webapp Deployment`, whose Details link in the checks list opens the deploy (a job's own
Details link opens its log).

Setup, once per repository: create the Pages project(s) with
`npx wrangler pages project create <name> --production-branch main`, then in the GitHub
repository set the secret `CLOUDFLARE_API_TOKEN` (permission Cloudflare Pages: Edit) and the
variables `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_PAGES_APP_PROJECT`
(`CLOUDFLARE_PAGES_STORYBOOK_PROJECT` for a Storybook site). Without
`CLOUDFLARE_PAGES_APP_PROJECT` the deploy jobs are skipped, and so are **lighthouse** and **e2e**,
which follow them. Once the app has a backend, set `VITE_API_URL` on the `pnpm build` step of
**check**, and upload `apps/web/dist/` from there as the `app` artifact instead of the mock build
**check** uploads.

The **e2e** job builds an Allure 3 report (`apps/web/allurerc.ts`; its history carried in the
Actions cache). With the variable `CLOUDFLARE_PAGES_PROJECT` set (plus `CLOUDFLARE_ACCOUNT_ID` and
the secret `CLOUDFLARE_API_TOKEN`, permission Cloudflare Pages: Edit), it publishes it on Cloudflare
Pages, and uploads it as an artifact only when it cannot go there (no project, or a failed
deploy): `<project>.pages.dev`, linked from the run's summary page. It checks what Pages serves in
production. Create the project once:
`npx wrangler pages project create <name> --production-branch main`.

The **check** job publishes the unit tests' coverage report (Vitest's HTML, `apps/web/coverage/`)
the same way, on a second Pages project named by the variable `CLOUDFLARE_PAGES_UT_PROJECT` (same
account and token; a project of its own, since a project has one `main` deploy), linked from the
commit status `Unit coverage report`; the `coverage` artifact only when it cannot go there. Vitest
writes no report when a test fails.

### Before real users

What ships is production-shaped (security headers and a Content-Security-Policy, hashed assets
cached for a year, a stale tab reloaded once after a deploy, no mock code in a `pnpm build`), but a
new project still runs as a demo until these are done:

- **Backend:** the paragraph above (`VITE_API_URL`, `build` instead of `build:mock`).
- **Content-Security-Policy:** in `apps/web/vite.config.ts`, narrow `connect-src` from `https:` to
  the API's origin.
- **Token storage** (with authentication): `apps/web/src/lib/api/token.ts` keeps the bearer token
  in localStorage, which any script on the page can read; move it to an httpOnly cookie once the
  backend supports one. There is no refresh token: a 401 ends the session.
- **Error reporting:** every unexpected error (a route that throws, a 5xx, a response that breaks
  its schema) goes through `reportError` in `apps/web/src/lib/report-error.ts`, which writes to the
  console; call the error tracker there and the whole app reports to it.
- **Repository settings:** turn on Dependabot security updates (`.github/dependabot.yml` already
  opens the weekly update pull requests), and protect `main` with `.github/rulesets/main.json`: no
  deletion or force push, changes through a squash-merged pull request, and the five checks above
  (a skipped deploy job, as on a Dependabot pull request, counts as passed). A repository admin
  applies it once: `gh api -X POST repos/<owner>/<repo>/rulesets --input .github/rulesets/main.json`
  (or Settings > Rules > Rulesets > Import). After renaming a job, update its name there.
- **Custom domain:** the app is served at `<project>.pages.dev`; add a domain under the Pages
  project's Custom domains.

## Package roadmap

Not created yet, create only when the trigger fires:

| Candidate | What moves in | Trigger | Notes |
|---|---|---|---|
| `@repo/schemas` | Shared Effect Schema DTOs | 2 apps read the same resource | Feature-local schemas stay in the feature. |
| `@repo/test-utils` | `createTestQueryClient`, setup polyfills and MSW lifecycle, render helpers as factories | A 2nd app with tests | The app keeps a thin `src/test/render.tsx`. |
| `@repo/mocks` | Shared MSW handlers and fixtures for a shared backend | 2 apps mock the same endpoints | Goes with `@repo/schemas`. |
| `@repo/utils` | Domain-free pure helpers (formatting, ...) | A helper needed by 2+ packages | Business rules stay in each feature's `model.ts`. |
| `@repo/constants` | Only values shared across apps | A value really shared | Do not make it a junk drawer; prefer colocating. |
| `@repo/hooks` | Non-UI React hooks (UI hooks go in `@repo/ui/hooks`) | A hook needed by 2+ apps | |
| `@repo/storybook-config` | The shared `.storybook` | 3+ apps with an identical `.storybook` | |

## Project generator (`create/`)
